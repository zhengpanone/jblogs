==========
LLM 模型
==========

概述
-------------------------

LLM（Large Language Model，大语言模型）位于 RAG 技术栈的「大语言模型」层，是整个系统的**生成引擎**。
它接收检索与排序模块召回的文档片段（Context），结合用户问题（Query）组装成 Prompt，最终生成自然语言答案。

在 RAG 架构中，LLM 处于承上启下的位置：

- **向下**：消费向量数据库与 Rerank 模型返回的结果，只负责"读懂并表达"，不负责"记忆知识"。
- **向上**：被 LLM 框架（LangChain、LlamaIndex、Spring AI 等）封装调用，对业务层暴露统一接口。

因此评价一个 RAG 系统时，检索层决定"能不能找到"，而 LLM 决定"能不能说清"。

.. note::

  本节讨论的是**生成模型**（Generative Model）。RAG 技术栈中的「嵌入模型」层虽然也属于大模型范畴，
  但它输出的是向量而非文本，两者的选型标准完全不同，详见下文"嵌入模型与生成模型的区别"一节。


模型分类
-------------------------

按能力划分
>>>>>>>>>>>>>>>>>>>>>>>>

.. list-table::
   :widths: 15 30 25 30
   :header-rows: 1

   * - **类型**
     - **说明**
     - **典型用途**
     - **代表模型**
   * - 通用对话模型
     - 指令遵循能力强、成本低、首字延迟小，是最常用的默认选择
     - 知识问答、摘要、改写、分类、信息抽取
     - GPT-4o、Claude、DeepSeek-V3、Qwen-Plus
   * - 推理模型
     - 生成答案前先进行较长的内部思考，擅长多步推导与自我校验
     - 数学证明、复杂代码、多跳问答、Agent 决策
     - OpenAI o 系列、DeepSeek-R1、QwQ、Qwen3 思考模式
   * - 多模态模型
     - 支持图像、音频、视频等非文本信号的输入或输出
     - 图片理解、图表问答、OCR 增强、语音交互
     - GPT-4o、Gemini、Qwen-VL、Qwen-Omni
   * - 嵌入 / 重排模型
     - 把文本或图像映射成向量、或对候选文档重新打分，自身不生成答案
     - 向量化索引、召回、Rerank
     - text-embedding-v3、bge-m3、bge-reranker

按部署方式划分
>>>>>>>>>>>>>>>>>>>>>>>>

- **云端 API**：由厂商托管，能力最强、免运维，按 Token 计费。适合快速验证与通用业务。
- **开源权重自部署**：下载模型权重后在自有 GPU 上推理，数据不出内网，可做微调。适合数据敏感场景。
- **本地轻量模型**：通过 Ollama、LM Studio 等工具在本机运行量化后的小模型。适合个人开发与离线演示。

按参数规模划分
>>>>>>>>>>>>>>>>>>>>>>>>

参数量越大通常能力越强，但成本与延迟也越高。实际落地更常见的做法是**大小模型配合**：
用小模型做路由、意图识别、查询改写，用大模型做最终生成与复杂推理。


通用对话模型
-------------------------

这是 RAG 系统中使用频率最高的一类模型，特点是响应快、指令遵循稳定、价格可控。
在知识问答场景下，配合检索到的上下文，通用模型已经足以覆盖绝大多数需求。

使用要点：

- 通过 ``system`` 角色约束模型的回答边界，例如"只依据上下文回答，找不到就说不知道"。
- 让模型**标注引用来源**（文档名或片段编号），便于人工核验、降低幻觉风险。
- 中文场景优先选择中文语料占比高的模型，术语理解与表达习惯会更好。


推理模型
-------------------------

主要特点
>>>>>>>>>>>>>>>>>>>>>>>>

推理模型（Reasoning Model）在输出最终答案之前，会先生成一段**思考过程**（Chain of Thought，思维链），
在思考中完成拆解、试错与自我校验，再给出结论。其行为特征与普通对话模型有明显差异：

- **延迟更高**：思考过程会消耗额外的 Token 与时间，首字延迟明显变长。
- **准确率更高**：在数学、逻辑、多跳检索问答上提升显著。
- **输出更长**：最终答案之外还会产生 ``reasoning_content`` 等思考字段。

代表模型
>>>>>>>>>>>>>>>>>>>>>>>>

- **OpenAI o 系列**：推理模型的代表，适合复杂规划与代码任务。
- **DeepSeek-R1**：开源推理模型，可自部署，性价比高。
- **QwQ / Qwen3 思考模式**：同一模型可开关思考能力，灵活平衡成本与效果。

使用注意
>>>>>>>>>>>>>>>>>>>>>>>>

- 推理模型**通常不建议**自行调节 ``temperature`` 和 ``top_p``，容易干扰其推理稳定性，保持默认即可。
- 部分实现中思考内容通过独立字段返回，不要把思考过程直接展示给终端用户。
- 思考 Token 同样计费，需要为 ``max_tokens`` 预留足够空间，否则会出现"思考完成却没有答案"的截断。
- 简单抽取式问答（如"这个值是多少"）用推理模型收益有限，反而白白增加延迟与成本。


多模态模型
-------------------------

能力维度
>>>>>>>>>>>>>>>>>>>>>>>>

多模态模型打破了"纯文本输入输出"的限制，在 RAG 中主要用于解决**文档中的非文本内容**问题：

- **图像理解**：识别扫描件、截图、流程图、手写内容。
- **图表问答**：读取折线图、柱状图中的数据并回答趋势类问题。
- **语音 / 视频**：将音频转写为文本，或从视频帧中提取关键信息。
- **跨模态检索**：用文本检索图片，或用图片检索文本。

代表模型
>>>>>>>>>>>>>>>>>>>>>>>>

- **GPT-4o / Gemini**：原生多模态，文本、图像、音频统一建模。
- **Qwen-VL 系列**：中文场景下的视觉语言模型，OCR 与中文图表理解表现较好。
- **Qwen-Omni 系列**：支持语音输入与语音输出的端到端全模态模型。

多模态 RAG
>>>>>>>>>>>>>>>>>>>>>>>>

传统 RAG 只处理纯文本，遇到 PDF 中的图表、截图、表格就会丢失信息。多模态 RAG 的常见做法是：

#. **解析**：用视觉模型把图片、图表转成文本描述（Caption）或直接做 OCR。
#. **索引**：把描述文本与原文文本一起向量化，写入向量数据库。
#. **生成**：检索到图片描述后，交由多模态 LLM 结合原图生成答案。

对算力或成本敏感的场景，也可以只在离线解析阶段使用多模态模型，在线问答阶段仍用纯文本模型，
这样既能保留图表信息，又不会增加每次问答的成本。


关键参数
-------------------------

.. list-table::
   :widths: 25 20 55
   :header-rows: 1

   * - **参数**
     - **常用取值**
     - **说明**
   * - ``temperature``
     - 0 ~ 0.7
     - 采样温度。越低输出越确定、越保守；越高越发散、越有创造性。
   * - ``top_p``
     - 0.7 ~ 0.9
     - 核采样概率阈值。与 ``temperature`` 一般只调其一即可。
   * - ``max_tokens``
     - 按场景设定
     - 单次生成的最大 Token 数，需为 Prompt + 检索上下文预留剩余额度。
   * - ``context_window``
     - 8K ~ 数百 K
     - 模型的上下文窗口上限，决定一次能塞入多少召回内容。
   * - ``stream``
     - ``True`` / ``False``
     - 是否流式返回。对话类产品建议开启，显著降低用户感知延迟。
   * - ``seed``
     - 整数
     - 固定随机种子，配合低温度可提升结果可复现性，便于回归测试。
   * - ``stop``
     - 字符串或列表
     - 遇到指定内容立即停止生成，常用于截断模型的多余发挥。

RAG 场景的推荐配置：

- **抽取式问答**：存在标准答案，追求稳定与可复现，建议 ``temperature=0``。
- **归纳与改写**：摘要、润色类任务，需要兼顾准确与流畅，建议 ``temperature=0.3 ~ 0.7``。
- **推理模型**：保持参数默认，不要手动设置 ``temperature``。


嵌入模型与生成模型的区别
-------------------------

这是 RAG 入门最容易混淆的一点，两者虽然都叫"模型"，但职责完全不同：

.. list-table::
   :widths: 20 40 40
   :header-rows: 1

   * - **维度**
     - **嵌入模型**
     - **生成模型（LLM）**
   * - 职责
     - 召回：把内容变成向量，算相似度
     - 生成：读上下文，产出自然语言答案
   * - 输出
     - 固定维度的浮点数向量
     - 文本（或结构化内容）
   * - 调用时机
     - 离线建索引 + 在线召回
     - 仅在线生成
   * - 关注指标
     - 召回率、向量维度、相似度分布
     - 准确率、幻觉率、延迟、成本
   * - 更换代价
     - 高，需要重新全量向量化
     - 低，改配置即可切换

**排查 RAG 效果问题时的经验法则**：先确认检索层是否召回了正确片段，
如果召回正确但答得不对，才需要调整 LLM 或 Prompt。


调用示例
-------------------------

云端 API 调用
>>>>>>>>>>>>>>>>>>>>>>>>

以 OpenAI 兼容接口为例，把检索到的上下文注入 Prompt：

.. code-block:: python

  from openai import OpenAI

  client = OpenAI(
      api_key="sk-xxx",
      base_url="https://dashscope.aliyuncs.com/compatible-mode/v1",
  )

  prompt = f"""请仅根据以下上下文回答问题，不要使用上下文之外的知识。
  如果上下文中没有答案，请直接回答"未找到相关信息"，并标注引用来源。

  上下文：
  {context}

  问题：{question}
  """

  response = client.chat.completions.create(
      model="qwen-plus",
      messages=[
          {"role": "system", "content": "你是一个严谨的问答助手。"},
          {"role": "user", "content": prompt},
      ],
      temperature=0.2,
      top_p=0.8,
      max_tokens=1024,
  )
  print(response.choices[0].message.content)

流式输出
>>>>>>>>>>>>>>>>>>>>>>>>

.. code-block:: python

  stream = client.chat.completions.create(
      model="qwen-plus",
      messages=messages,
      stream=True,
  )
  for chunk in stream:
      if chunk.choices and chunk.choices[0].delta.content:
          print(chunk.choices[0].delta.content, end="", flush=True)

推理模型（思考模式）
>>>>>>>>>>>>>>>>>>>>>>>>

.. code-block:: python

  response = client.chat.completions.create(
      model="qwen3-8b",
      messages=[{"role": "user", "content": "请推导出该结论的每一步依据。"}],
      extra_body={"enable_thinking": True},
  )
  # 思考过程，可用于调试，不建议直接展示给终端用户
  print(response.choices[0].message.reasoning_content)
  # 最终答案
  print(response.choices[0].message.content)

本地模型（Ollama）
>>>>>>>>>>>>>>>>>>>>>>>>

Ollama 同样提供 OpenAI 兼容接口，切换成本极低：

.. code-block:: python

  client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")

  response = client.chat.completions.create(
      model="qwen2.5:7b",
      messages=[{"role": "user", "content": "你好"}],
  )


选型建议
-------------------------

#. **先看上下文窗口**：确保能装下 ``top_k`` 召回内容 + Prompt 模板 + 历史对话，再谈其它指标。
#. **中文优先国产模型**：中文语料占比更高，术语与表达习惯更贴合，价格通常也更有优势。
#. **按任务分层选型**：意图识别、查询改写用小模型；最终生成、复杂推理用大模型；多跳问答再上推理模型。
#. **评估成本与延迟**：线上高并发场景要同时核算 Token 单价、平均响应时长与首字延迟。
#. **数据敏感走本地部署**：金融、医疗、政务等场景优先考虑开源模型自部署，保证数据不出内网。
#. **保持一层抽象**：统一使用 OpenAI 兼容接口或 LLM 框架，避免与单一厂商深度绑定，方便随时切换模型。
#. **建立评测集**：用固定的问答对与参考答案做回归，模型升级或换 Prompt 时才能量化对比效果。
